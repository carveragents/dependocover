# Dependocover

Dependocover scans Python, JavaScript/TypeScript, Java, C, C++, and C# repositories and collects
evidence about what may be needed to run them: package dependencies, containers,
cloud resources, outbound HTTP/API calls, databases, queues, and service providers.

It uses static analysis only. It does not import, install, or execute the
repository being scanned. Findings include file and line locations, but may
include development dependencies, tests, docs, examples, or unused code.
Treat the report as a reviewable inventory, not a definitive environment spec.

## Install and run

Requires Python 3.10 or newer. From a checkout:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install --editable .
dependocover /path/to/repository
```

You can scan a public GitHub repository directly as well:

```bash
dependocover https://github.com/owner/repository
```

The command makes a shallow clone to a temporary directory, scans the
checkout, and removes it when scanning finishes. Git must be installed.
Private repositories work when your local Git credential helper already has
access; Dependocover does not ask for or store GitHub credentials. The current
implementation caps the checkout at 500 MB by default and the clone at 180 seconds.
Raise the limit for large repositories with `--max-repository-size-mb`, for example:

```bash
dependocover https://github.com/elastic/elasticsearch --max-repository-size-mb 2000
```

Produce JSON for tools or save it to a file:

```bash
dependocover /path/to/repository --format json --output report.json
```

For a batch of repositories, write a separate report per scan. Each filename
includes the repository identifier and revision when available:

```bash
dependocover https://github.com/owner/repository --format json --output-dir ./reports
```

For many repositories, put one URL or local checkout path per line in a text
file (blank lines and `#` comments are ignored), then run:

```bash
dependocover --batch-file repositories.txt --format json --output-dir ./reports
```

If some repositories fail, their URLs are written to `reports/failed-runs.txt`.
Retry only those repositories with:

```bash
dependocover --batch-file repositories.txt --format json --output-dir ./reports --retry-failed
```

The retry mode reads `failed-runs.txt` from the output directory and leaves
successful repositories from the original batch untouched. Repositories that
still fail remain in the refreshed `failed-runs.txt` for another retry.

Batch mode writes both a machine-readable `.json` report and a readable `.txt`
inventory per repository when `--format json` or `--format both` is selected.
Use `--format text` to write only the text report.
Reports are written under `<output-dir>/<repository>-<commit>/inventory.json`
and `inventory.txt`.

The output folder is named with the repository ID and Git revision. When a
local directory has no Git revision, a stable hash of its input path prevents
same-named directories from overwriting one another.

You can also use `python -m dependocover.cli /path/to/repository`.

## Initial coverage

This release does **not** build a general code index, call graph, or runtime
dependency graph. It walks eligible files, parses Python files into Python's
AST (abstract syntax tree), and applies targeted checks:

- Python AST parsing extracts `import` and `from ... import ...` statements. Warnings
  generated by invalid escape sequences in scanned Python source are suppressed. This is
  syntax-aware, but does not resolve imports, follow call paths, evaluate
  dynamic imports, or determine which imports execute in production.
- JavaScript/TypeScript imports and CommonJS `require()` statements are read
  with targeted syntax patterns; npm dependencies are read from `package.json`
  and versions from `package-lock.json`/`npm-shrinkwrap.json` when present.
- Java imports are read from `.java` files. Maven `pom.xml` dependencies and
  common Gradle dependency declarations are parsed, including declared versions.
- C# `using` directives are inventoried, and NuGet dependencies are read from
  `.csproj`, `.props`, `.targets`, and legacy `packages.config` files.
- C and C++ `#include` directives are inventoried with a standard-header
  exclusion list. Common native dependency declarations are read from CMake
  `find_package`, Conan files, and vcpkg manifests. Header names are clues and
  may not map one-to-one to package names.
- `requirements*.txt` and `pyproject.toml` are parsed for declared Python
  packages and Python runtime requirements.
- Dockerfiles and Compose files are checked for base images and service image
  or build declarations.
- Selected Python/config files are scanned line by line for known SDKs,
  service libraries, connection strings, environment-variable names, and URL
  literals. These are pattern matches and can produce false positives.

The result is an evidence inventory from syntax parsing plus targeted text and
manifest parsing, not a whole-program code index.

## Environment inventory output

The JSON includes `metadata.repository` (input URL/path, repository ID,
canonical URL, Git tag/description, commit, branch, package version, dirty
state for local checkouts, and scan timestamp) so reports from many repositories
remain attributable to the exact revision.

`inventory` deduplicates findings into:

- `libraries`: declared package constraints/versions, import names, source
  manifests, ecosystem (`python`/`npm` evidence), and locations.
- `services.internal`: services declared in Docker Compose, with image/build
  declarations and visible ports, environment key names, volumes, and related
  settings.
- `services.standard_cloud`: AWS, Google Cloud, and Azure clues, including
  recognized SDKs and configuration parameter names.
- `services.third_party`: named provider SDK/service clues such as OpenAI,
  Anthropic, Stripe, email, and observability providers.
- `api_endpoint_candidates`: URLs from recognized request calls, with HTTP
  methods, query/request parameter names, hosting classification, and locations.
- `url_references`: all extracted URLs, including document links and repository
  metadata links. `findings` is deduplicated by category, name, and details;
  each entry has `locations` and distinct `evidence` lists. Normalized URLs are
  available at `findings[].details.url`.
- `configuration_parameters` and `environment`: visible environment key names,
  Docker images/tags, exposed ports, and infrastructure declarations.

The scanner stores parameter names and redacts common credential-shaped values.
Dynamic URLs, dynamically assembled request bodies, and deployment-specific
values still require configuration or runtime evidence. Database and broker
clients are labeled `internal_or_managed_unknown` unless deployment files show
where they run.

The text report includes the deduplicated inventory in readable sections.
Each service includes a subcategory such as `vector_database`, `email_delivery`,
`llm_api`, or `relational_database`.

Service categories and subcategories use a versioned controlled vocabulary
(`taxonomy_version: 1.0`). A service record groups its recognized endpoints,
request parameter names, configuration key names, deployment parameters,
and evidence locations. It does not store configuration values or secrets.

Informational URLs are separated from operational API endpoints using evidence
such as recognized research/document hosts, document file extensions, markdown
links, package metadata fields, and docs/examples paths. This is deterministic
filtering; no LLM call is made. A model such as Luna could be added as an
optional review step for ambiguous URLs, but it should not be required for a
repeatable scan across many public repositories.

## Service classification rules

Classification is based on explicit indicators, not a general claim that a
service is “well known”:

- **Internal:** a service declared in Docker Compose; or a URL using localhost,
  a private-service hostname pattern, or another local marker.
- **Standard cloud:** a recognized cloud SDK/configuration clue (for example,
  boto3/AWS variables) or a hostname under known AWS, Google Cloud, or Azure
  endpoint domains.
- **Third party:** a recognized provider SDK/configuration clue (for example,
  OpenAI, Anthropic, Stripe, or email providers), or a URL under a provider
  domain explicitly listed in the scanner.
- **Unclassified:** URLs and HTTP calls that do not match those rules. The
  scanner leaves these unresolved rather than guessing from a generic URL.

Provider/domain matches are maintained as code in `scanner.py`; this is a
finite recognition list and will need additions as the scanner learns new
providers. A detected database SDK does not reveal whether the database is
self-hosted or managed, so that remains `internal_or_managed_unknown` absent
deployment evidence. Variable URL ports such as `:PORT` are retained as
placeholders and omitted from numeric port fields.

- Imports and dependency manifests for Python, JavaScript/TypeScript, Java,
  C, C++, and C#.
- Node.js/package-manager runtime requirements from npm project metadata.
- Dockerfiles and Docker Compose image/build declarations.
- Recognizable AWS, Google Cloud, and Azure SDK/configuration references.
- Common database, queue, email, payment, messaging, and HTTP client clues.
- URLs and selected cloud/service configuration names.

This first release does not resolve every import to a package distribution,
deeply parse Terraform/CDK, infer all required environment variables, or find
endpoints constructed dynamically at runtime. No code from a scanned project
is executed.

## macOS DMG direction

The scanner API (`scan_repository`) is separate from the CLI, so a future GUI
can call the same core directly. Keep this core cross-platform. First publish
the Python package to PyPI for easy CLI installation (for example,
`pipx install dependocover`). When the GUI is ready, bundle a small `.app` with
Briefcase or PyInstaller, then distribute the signed/notarized app in a DMG
using `create-dmg` or Apple's `hdiutil`. A DMG is a delivery container; the
application inside it is the GUI wrapper and bundled Python runtime.
